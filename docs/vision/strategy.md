# Vision 2026-2027
## Миссия
Заменить ATAS, CScalp для трейдеров
Заменить MetaTrader для разработчиков стратегий и роботов

## Цели
- Q2 2026: MVP с Binance/Bybit
- Q3 2026: Paper Trading + 5 индикаторов
- Q4 2026: Live Trading + монетизация

## Целевая аудитория
- Криптотрейдеры, использующие Volume Profile
- Алготрейдеры, пишущие на Kotlin/Python/JS
- Бывшие пользователи ATAS

Техническое задание (предварительная версия v0.1)
Проект: Разработка кроссплатформенного трейдингового терминала для криптобирж (MVP)
Цель: Создать замену платформе ATAS с фокусом на крипторынки, начиная с Binance и Bybit.
Статус: Анализ и проектирование MVP.

1. Бизнес-требования и цели
   Продукт: Десктопное приложение (Windows/macOS/Linux), построенное по модульной архитектуре ("оконный" терминал).
   Целевая аудитория: Криптотрейдеры, использующие анализ рыночного объема (Volume Profile, Order Flow, Market Delta).
   Ключевое отличие от ATAS: Фокус на крипторынки, современный стек (Kotlin, Compose), модульность.
   Этапы развития:
   Этап 1 (MVP): Только чтение данных с рынка (Spot & Futures) с Binance и Bybit. Без авторизации, без торговли.
   Этап 2 (Paper Trading): Добавление авторизации по API-ключам и возможности бумажной торговли.
   Дневник трейдера. С оффлайн базой дневника и истории сделок.
   Инструменты статистического и портфельного анализа.
   Этап 3 (Live Trading): Реальная торговля.
   Будущее: Поддержка других криптобирж, расширение индикаторов, алготрейдинг.
   API для быстрой проверки гипотез с помощью AI.
   API для анализа рынка по агрегированным и сырым данным order flow
   Поддержка плагинов indicators, strategy (history), robot realtime trading (если нужно)

2. Функциональные требования (Scope MVP - Этап 1)
   2.1. Модуль подключения к данным (Data Feed)
   Подключение к публичным WebSocket и REST API Binance и Bybit.
   Получение и агрегация сырых данных:
   Стакан заявок (Order Book).
   Поток сделок (Time & Sales / Trade Flow).
   Свечные данные (OHLCV).
   НЕ требуется: Авторизация, управление аккаунтом, работа с ордерами.
   2.2. Модуль отображения рыночных данных (UI-Терминал)
   Приложение должно состоять из главного окна и открываемых из него модульных окон. Окна должны быть перетаскиваемыми, изменяемыми в размере, закрываемыми.
   Главное окно:
   Панель выбора биржи (Binance/Bybit) и типа рынка (Spot/Futures).
   Панель выбора торгового инструмента (например, BTCUSDT).
   Кнопки для открытия модульных окон: "График", "Стакан", "Order Flow".
   Модульное окно "График":
   Отображение свечного графика (таймфреймы: 1m, 5m, 15m, 1h и т.д.).
   Базовые индикаторы (заимствованные из ATAS): Например, VWAP, Moving Averages, Volume Profile (начальная версия). Отображение дельта-баров (разница между объемом на Bid и Ask).
   Возможность переключения между отображением свечей и дельта-баров.
   Модульное окно "Стакан" (Depth of Market):
   Табличное или графическое отображение бидов и асков с динамическим обновлением.
   Модульное окно "Order Flow / Time & Sales":
   Таблица потока рыночных ордеров в реальном времени.
   Визуальное выделение крупных ордеров ("блоков").
   2.3. Серверная часть (Backend Adapter - MVP)
   Роль: Адаптер, агрегатор и кэш данных. Получает сырые данные с бирж, агрегирует, хранит и отдает клиенту по единому API.
   Функции в MVP:
   Подписка на потоки данных с бирж (WebSocket).
   Агрегация потоковых данных в минутные бары (1m) со следующей структурой (продумать!):
   timestamp, open, high, low, close, volume.
   bid_volume, ask_volume, delta (bid_volume - ask_volume).
   number_of_trades.
   Флаг/маркер наличия крупного ордера (block trade) в этот интервал и его примерный объем.
   Запись агрегированных минутных баров в БД (например, PostgreSQL или TimescaleDB для временных рядов).
   Предоставление REST/WebSocket API клиенту для:
   Получения списка инструментов.
   Получения исторических свечных данных (уже из своей БД).
   Подписки на реаль-тайм обновления стакана и потока сделок (стриминг с бирж через бэкенд).

3. Нефункциональные требования
   Производительность: Минимальные задержки в отображении рыночных данных (< 500 мс от события на бирже до UI).
   Надежность: Стабильное поддержание WebSocket-соединений, обработка реконнектов.
   Масштабируемость архитектуры: Возможность добавления новых бирж и индикаторов без переписывания ядра.
   Качество кода: Чистая архитектура, тестируемость.

4. Технический стек и архитектура (Предложения)
   4.1. Клиентская часть (Kotlin Multiplatform)
   Язык: Kotlin.
   UI: Jetpack Compose для Desktop. Отличный выбор для модульных окон.
   Архитектура: Рекомендую MVI (Model-View-Intent) или MVVM с четким разделением слоев:
   Data Layer: Репозитории, которые общаются с вашим бэкенд-API (REST/WebSocket).
   Domain Layer: UseCases (интерфакторы), содержащие бизнес-логику (например, преобразование данных для графика).
   Presentation Layer: ViewModel (или MVI-Store) + Composable-экраны (окна).
   Мультиплатформа: Общий код (модели данных, репозитории, use cases) выносится в commonMain. Платформенно-специфичный код (например, настройки окна, системные уведомления) — в desktopMain.
   Графики: Для отрисовки свечей и индикаторов потребуется кастомная реализация на Canvas Compose или использование готовой библиотеки, совместимой с Compose Desktop (например, TradingView Light Charts или аналоги, но может потребоваться интеграция). Это ключевая техническая сложность.
   4.2. Серверная часть
   Язык/Фреймворк: Ktor — отличный выбор, если команда хочет остаться в экосистеме Kotlin. Это позволит переиспользовать модели данных и часть логики между клиентом и сервером. Node.js может быть быстрее для прототипирования из-за богатой экосистемы для крипто-API, но Kotlin/Ktor обеспечит лучшую типобезопасность и долгосрочную поддерживаемость для Kotlin-команды.
   База данных: PostgreSQL с расширением TimescaleDB (для эффективного хранения временных рядов) или ClickHouse (если объем данных будет огромным).
   Кеширование/Стриминг: Redis (для кеширования стаканов, последних сделок) + Ktor WebSockets для стриминга данных клиентам.
   4.3. Интеграция индикаторов из ATAS (C#)
   Проблема: Индикаторы на C# не могут быть напрямую использованы в Kotlin.
   Варианты решения:
   Порт кода: Вручную переписать логику индикаторов на Kotlin. Это наиболее правильный и производительный путь для MVP. Начните с 2-3 ключевых индикаторов.
   Микросервис: Запустить .NET Core сервис, который будет вычислять индикаторы, и общаться с ним по gRPC. Слично сложно для MVP.
   Использовать готовые библиотеки: Поискать Java/Kotlin библиотеки для технического анализа (например, ta4j), но они могут не содержать специфичных для order flow индикаторов.
   Рекомендация для MVP: Вариант 1 (порт). Фокусируйтесь на логике, а не на точном воспроизведении пикселей. Визуализацию делайте через Compose Canvas.

5. Предложения по первоначальному этапу (Roadmap)
   Неделя 0: Уточнение и прототип.
   Задача: Получить сырые данные с WebSocket Binance (стакан, сделки) и вывести в консоль через небольшое Kotlin-приложение (можно Ktor-клиент).
   Задача: Создать простейшее Compose Desktop приложение с двумя перетаскиваемыми окнами (прототип UI).
   Неделя 1-2: Бэкенд-адаптер (ядро данных).
   Настроить подключение к Binance/Bybit WebSocket.
   Реализовать агрегацию потоковых данных в минутные бары (в памяти).
   Настроить сохранение этих баров в БД (схему продумать заранее!).
   Сделать простой REST эндпоинт для отдачи исторических данных.
   Неделя 3-4: Клиент - основа и первый график.
   Настроить проект KMP (клиент + общий модуль).
   Реализовать связь клиента с бэкендом (получить список инструментов, исторические данные).
   Реализовать отрисовку простых свечей на Canvas Compose в отдельном окне.
   Связать подписку на реаль-тайм данные (через бэкендный WebSocket) и обновление графика.
   Неделя 5-6: Расширение функционала.
   Добавить окно стакана.
   Добавить окно Order Flow.
   Портировать 1-2 ключевых индикатора из ATAS (начните с дельты) и отображать их на графике.
   Неделя 7-8: Интеграция и полировка.
   Интегрировать Bybit API.
   Добавить настройки (выбор биржи, инструмента).
   Тестирование, исправление багов, профилирование производительности.

6. Оценка времени на MVP (Условная)
   Контекст: 1 разработчик с опытом Android/Compose (но новичок в KMP) + активное использование ИИ (Copilot, ChatGPT, Cline) для написания boilerplate кода, поиска примеров, решения стандартных проблем.
   Оценка: 250-400 человеко-часов (около 6-10 полных рабочих недель).
   Риски, увеличивающие срок:
   Сложности с отрисовкой производительных и сложных графиков в Compose.
   Необходимость глубокого понимания математики специфических индикаторов ATAS.
   Проблемы со стабильностью WebSocket-соединений и обработкой всех кейсов бирж.
